Embedded touchscreen UI for combine harvesters.

I designed UI features for the embedded touchscreen systems on John Deere combine harvesters, translating new hardware capabilities into updated interaction patterns and control layouts, and drove adoption of Deere’s Embedded Systems UX/UI standards across IT delivery teams worldwide.

Role
UX Designer, contract
Where
Moline, IL
When
Dec 2018 – Jul 2019
Surface
Embedded touchscreen displays

Public Note

This work is confidential. The case study covers responsibilities, methods, and collaboration patterns; interface screens for Deere’s embedded products are not shown.

Context

An embedded machine interface is not a consumer app. The operator is mid-task inside a harvester, the environment is loud and physically demanding, gloves are likely, and a misread state carries real operational cost in a season measured in days. The display also has to work in direct sunlight and in the dark.

Those constraints move the design questions away from visual novelty and toward legibility, state clarity, and predictability — the operator should never have to look twice to know what the machine is doing.

What I Designed

New hardware capabilities kept arriving faster than the interface patterns that would expose them. My work was translating each capability into controls an operator could use without retraining.

Interaction patterns

Turned new harvester hardware capabilities into updated interaction patterns and control layouts for the embedded touchscreen.

HCI methods

Applied HCI methods to clarify workflows, interface states, and the usability considerations specific to operating a machine.

Hardware collaboration

Worked with hardware engineers and product teams to keep UI decisions aligned with the constraints of the embedded system.

Standards Adoption

A standard only matters if delivery teams actually reach for it. Beyond contributing to Deere’s Embedded Systems UX/UI standards, a large part of the job was driving their adoption across IT delivery teams worldwide, which meant the documentation had to be findable, current, and specific enough to answer real implementation questions rather than restate principles.

I improved the UI documentation workflows behind that, so the standards stayed maintainable and the teams using them could keep up with changes.

What I Took From It

This is where the habit I still work by started: treat the documented pattern as the product and the individual screen as an instance of it. The same instinct shows up now in component APIs — the reusable thing is the real deliverable, and a screen is just one of its outputs.
